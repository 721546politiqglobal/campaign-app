# UI Internationalization (i18n) — Design

## Context

The app is English-only today: no i18n library, no locale concept anywhere
in the schema or session, and all copy is inline JSX strings across
`src/app/**/page.tsx` and `src/components/*.tsx` (~360 text nodes across
~50 files). The user wants the whole app to support other languages,
starting with Spanish.

This spec covers **UI translation only** — the app's interface (nav,
labels, forms, settings, validation/error messages). Translating
*generated campaign content* (Content Wizard output, HeyGen avatar
scripts/video, ElevenLabs voice, monitoring sources) is a separate,
independent subsystem with its own design, deferred to a follow-up spec.

Auth in this app is a custom HMAC-signed cookie session (`src/lib/session.ts`),
not Supabase Auth — `getSession()` re-fetches the user's row from `users` on
every call to catch role/removal changes. There is no `profiles` table;
`users` is the only per-user row.

## Goals

- Locale is a per-user account setting (not URL-based routing).
- Spanish is the first additional language; adding more later should be a
  small, code-only change (no schema migration per language).
- Authenticated pages render in the user's saved locale. Pre-auth pages
  (login, join, pricing) use browser-language detection with a manual
  toggle, persisted via cookie until the user has an account setting.
- Validation and server-action error messages are translated, not just
  static UI copy.
- Ship incrementally, in stages, rather than one large PR touching all
  ~50 files at once.

## Non-goals

- URL-based locale routing (`/es/...`).
- Translating generated campaign content, avatar scripts/voice, or
  monitoring data (follow-up spec).
- RTL layout support (not needed for the current language set).
- A translation-management/vendor pipeline — translation JSON is
  hand-maintained in-repo for this phase.

## Architecture

**Library:** `next-intl`, used in its "no routing" mode (locale resolved
per-request in code, no `[locale]` URL segment or locale middleware).

**Locale resolution** happens once per request via a new `getLocale()`
helper in `src/lib/locale.ts`:

1. Valid session cookie → decode the cookie's own `locale` field directly
   (no DB call — see below).
2. Else, a `locale` cookie (set by the pre-auth language toggle).
3. Else, parse the `Accept-Language` header.
4. Else, default to `'en'`.

The resolved locale must be checked against a `SUPPORTED_LOCALES = ['en',
'es'] as const` list in `src/lib/locale.ts` — any unrecognized value
(corrupted cookie, unsupported browser language) falls back to `'en'`.
Adding a language later means appending to this array and adding a
message file, not a migration.

**Root layout change:** `src/app/layout.tsx` becomes an async server
component. It calls `getLocale()`, renders `<html lang={locale}>`
dynamically (currently hardcoded `"en"`), loads `src/messages/{locale}.json`,
and wraps `children` in next-intl's `NextIntlClientProvider` alongside the
existing `ToastProvider`.

**Avoiding a duplicate DB round-trip:** this project's installed React
(`18.3.1`) does not export `cache` (a React 19 API) — `getSession()`
cannot be memoized that way. Instead, `locale` is carried directly inside
the signed session cookie payload (alongside the existing `role` /
`campaignId`), so the root layout's `getLocale()` decodes the cookie it
already has with **zero DB calls**. This doesn't touch or weaken
`getSession()`'s existing DB re-check of `role`/`campaignId` (that
security property — catching a removed/demoted user mid-cookie-life — is
unrelated to locale and is left exactly as-is). `getSession()` still adds
`locale` to its existing `select(...)` too (same query, no extra cost) so
pages that already call `requireSession()` (e.g. Settings, to pre-fill the
language dropdown) see the live DB value. When the user changes locale via
`updateLocaleAction`, the action re-signs the session cookie with the new
locale (in addition to updating the DB row) so the change is visible on
the very next request instead of waiting for the cookie to naturally
reissue.

## Data model

New migration (`supabase/migrations/0XX_user_locale.sql`):

```sql
alter table users
  add column if not exists locale text not null default 'en';
```

No `check` constraint — validity is enforced in application code
(`SUPPORTED_LOCALES`) so new languages don't require a migration.

`Session` (`src/lib/session.ts`) gains a `locale: string` field. It's
carried in the signed cookie payload (set at login/join/impersonate, and
re-set by `updateLocaleAction`) and also added to `getSession()`'s
existing `select(...)` so a live DB value is available wherever
`requireSession()`/`requireAdmin()` is already called — no extra query
either way.

## Components

- **`updateLocaleAction`** (new, in `src/app/settings/`): modeled on
  `team-actions.ts`'s `changeTeammateRoleAction` — `requireSession()` →
  validate against `SUPPORTED_LOCALES` → `adminDb.from('users').update({
  locale }).eq('id', s.userId)` → `revalidatePath('/settings')`. Exposed
  via a language dropdown in Settings.
- **Pre-auth language toggle**: small component in the login/join/pricing
  layout that sets the `locale` cookie and reloads. No account needed.
- **Message catalogs**: `src/messages/en.json` / `es.json`, namespaced to
  mirror the app (`common` for `Sidebar`/`AppFrame`/role labels/generic
  buttons, then `dashboard`, `settings`, `content`, `monitoring`,
  `analytics`, `avatars`, `billing`, `team`, `admin`, `auth`).
- Page/component copy is replaced with `useTranslations()` (client
  components) or `getTranslations()` (server components/actions).

## Error handling & validation

Per-feature validation modules (e.g. `src/lib/profile-validation.ts`) and
server-action error returns are rekeyed into `common.errors` / per-feature
namespaces and looked up via `getTranslations()` inside the action, using
the acting user's locale (already available from `requireSession()`).
Internal errors that are only logged (Stripe/webhook failures never shown
to a user) stay in English.

## Staged rollout

Each stage should build, typecheck, and pass tests before moving to the
next; stages are ordered by dependency and blast radius, not arbitrarily.

**Stage 0 — Foundation (infra, no visible translation yet)**
- `locale` migration (no check constraint) + `SUPPORTED_LOCALES`.
- Add `locale` to the `Session` type, the signed cookie payload (all 4
  `setSessionCookie` call sites), and `getSession()`'s `select(...)`.
- `getLocale()` helper: decode session cookie → pre-auth cookie →
  `Accept-Language` → default `'en'`.
- Install/configure `next-intl`; async root layout + `NextIntlClientProvider`.
- Empty `common`-only message catalogs (en/es).
- `updateLocaleAction` (updates DB row **and** re-signs the session
  cookie) + Settings dropdown; pre-auth cookie toggle.
- Unit tests: `getLocale()` resolution order, `updateLocaleAction`
  validation and cookie re-signing.

**Stage 1 — Shared chrome**
- `Sidebar`, `AppFrame` (incl. `ROLE_LABEL`), `Toast`, any other
  layout-level shared component rendered on every authenticated page.
- Verifies the plumbing end-to-end (switch locale in Settings, confirm nav
  re-renders in Spanish) before touching page content.

**Stage 2 — Core workflow pages**
- Dashboard, Content (list, `[id]`, new, `ContentWizard`), Settings page
  content itself. Highest-traffic surfaces.

**Stage 3 — Remaining authenticated pages**
- Monitoring, Analytics, Avatars, Billing, Team, Admin section.

**Stage 4 — Pre-auth pages**
- Login, Join, Pricing copy (toggle already exists from Stage 0).

**Stage 5 — Validation & error messages**
- Rekey `profile-validation.ts` and other validation/error strings;
  translate server-action error returns and toast copy.

**Stage 6 — Test & polish**
- Smoke-render a representative page per locale to catch missing keys
  (next-intl throws on missing keys by default — relied on rather than a
  hand-rolled coverage checker).
- Full `npm run typecheck` + `npm test` pass.

## Testing

- `getLocale()`: session → cookie → header → default, and invalid-value
  fallback to `'en'`.
- `updateLocaleAction`: rejects values outside `SUPPORTED_LOCALES`,
  persists valid ones, scoped to the caller's own row.
- Existing Vitest suite continues to run against default `'en'` copy — no
  changes needed since English remains the fallback/default locale.
- Missing-translation-key detection via next-intl's built-in throw
  behavior, exercised by the Stage 6 smoke render.

## Out of scope / follow-up

- Content-generation language support (Content Wizard, HeyGen, ElevenLabs,
  monitoring) — separate spec.
- Additional languages beyond Spanish — supported by the design but not
  scheduled here.
