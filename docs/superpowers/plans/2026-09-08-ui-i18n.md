# UI Internationalization (i18n) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the app's interface translatable, ship Spanish as the first additional language, with locale stored per-user and resolved without URL routing.

**Architecture:** `next-intl` (no locale routing) resolves the request's locale once in the root layout from the signed session cookie (falling back to a pre-auth cookie, then `Accept-Language`, then English). All literal UI strings move into `src/messages/en.json` / `es.json`, looked up via `useTranslations()` (client) / `getTranslations()` (server).

**Tech Stack:** Next.js 14.2.5 (App Router), React 18.3.1, `next-intl`, Supabase (Postgres), Vitest.

**Spec:** `docs/superpowers/specs/2026-09-08-ui-i18n-design.md`

## Global Constraints

- React `18.3.1` is installed — it does **not** export `cache` (React 19 API). Do not `import { cache } from 'react'` anywhere in this plan.
- No URL-based locale routing (no `/es/...` prefixes).
- `SUPPORTED_LOCALES = ['en', 'es'] as const`; default locale is `'en'`. No database `CHECK` constraint on `locale` — validity is enforced only in application code, so a third language later is a code-only change.
- Every literal user-facing string touched by this plan must end up in both `src/messages/en.json` and `src/messages/es.json` — no hardcoded English left behind in a file once its task is complete.
- Server-side text: `getTranslations('<namespace>')` from `next-intl/server`. Client components (`'use client'`): `useTranslations('<namespace>')` from `next-intl`.
- **Exception for `'use server'` action functions specifically** (not plain Server Components/pages): this codebase unit-tests server actions directly with Vitest, invoking the exported function with no real Next.js request in flight, so the ambient/request-scoped form of `getTranslations('<namespace>')` has nothing to read and will fail under test. Inside any `'use server'` function, call the explicit-locale form instead: `getTranslations({ locale: s.locale, namespace: '<namespace>' })` (using the acting user's locale from `requireSession()`). This form doesn't depend on request context, so it behaves identically in production and in a Vitest test that calls the action directly. If this form doesn't behave as expected when a task gets to it, the fallback is to mock `next-intl/server`'s `getTranslations` in the affected test file to return a stub translator function — note either outcome in that task's report.
- Follow existing patterns: `requireSession()` / `can(role, permission)` for auth checks, `throwOnError(...)` for Supabase writes, `revalidatePath(...)` after mutations.
- Run `npm run typecheck` and `npm test` after every task; both must pass before moving to the next task.
- Tasks that translate JSX (Stages 1–4) add no new automated tests — they're verified by `npm run typecheck`, the existing suite staying green, and a manual bilingual check (per-task Step 3/4 in the Stages 2–4 preamble). This is a deliberate scope decision, not a coverage gap: don't ask an implementer or reviewer to add rendering tests for these tasks.
- Every task from Task 6 onward that adds or changes a translation key touches `src/messages/en.json` and `src/messages/es.json` in addition to the files listed under that task's own **Files:** heading (omitted there for brevity, since nearly every task touches them) — always read the catalogs' current contents first and merge in new keys, never overwrite the file.

- [ ] **Step 4: Add `getLocale()` and `setLocaleCookie()` to `src/lib/locale.ts`**

```ts
import { cookies, headers } from 'next/headers';
import { peekSessionLocale } from './session';

export const SUPPORTED_LOCALES = ['en', 'es'] as const;
export type Locale = (typeof SUPPORTED_LOCALES)[number];
export const DEFAULT_LOCALE: Locale = 'en';

const LOCALE_COOKIE = 'locale';

export function isSupportedLocale(value: string | null | undefined): value is Locale {
  return !!value && (SUPPORTED_LOCALES as readonly string[]).includes(value);
}

// Picks the language the current request renders in:
// 1. The signed-in user's session cookie (peekSessionLocale — no DB call).
// 2. The `locale` cookie set by the pre-auth language toggle.
// 3. The browser's Accept-Language header.
// 4. DEFAULT_LOCALE.
export function getLocale(): Locale {
  const sessionLocale = peekSessionLocale();
  if (isSupportedLocale(sessionLocale)) return sessionLocale;

  const cookieLocale = cookies().get(LOCALE_COOKIE)?.value;
  if (isSupportedLocale(cookieLocale)) return cookieLocale;

  const acceptLanguage = headers().get('accept-language') ?? '';
  for (const tag of acceptLanguage.split(',')) {
    const lang = tag.trim().split(';')[0].split('-')[0];
    if (isSupportedLocale(lang)) return lang;
  }

  return DEFAULT_LOCALE;
}

export function setLocaleCookie(locale: Locale): void {
  cookies().set(LOCALE_COOKIE, locale, { path: '/', maxAge: 60 * 60 * 24 * 365, sameSite: 'lax' });
}
```

- [ ] **Step 3: Write `src/app/settings/locale-actions.ts`**

Modeled on `changeTeammateRoleAction` in `src/app/settings/team-actions.ts`, scoped to the caller's own row instead of a teammate's:

```ts
'use server';

import { revalidatePath } from 'next/cache';
import { requireSession, setSessionCookie } from '@/lib/session';
import { adminDb, throwOnError } from '@/lib/supabase';
import { isSupportedLocale } from '@/lib/locale';

// The 'Invalid language.' string is translated in Stage 5 along with the
// rest of the app's server-action error messages.
export async function updateLocaleAction(locale: string): Promise<{ ok: boolean; error?: string }> {
  const s = await requireSession();
  if (!isSupportedLocale(locale)) return { ok: false, error: 'Invalid language.' };

  await throwOnError(
    adminDb.from('users').update({ locale }).eq('id', s.userId),
    'users.update_locale',
  );

  // Re-sign the cookie so the new locale takes effect on the very next
  // request instead of waiting for the (up to 7-day-old) cookie to reissue.
  setSessionCookie({
    userId: s.userId,
    name: s.name,
    role: s.role,
    campaignId: s.campaignId,
    locale,
    exp: s.exp,
  });

  revalidatePath('/', 'layout');
  return { ok: true };
}
```
